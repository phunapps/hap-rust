## Lead

**hap-rust 1.0 — the first pure-Rust HomeKit (HAP) controller library.**

If you've wanted to talk to HomeKit accessories from Rust — discover them, pair
with a setup code, read/write characteristics, and stream change events — there
hasn't been a production-oriented library for it. `hap-rust` 1.0 fills that gap.
It's controller-side (what a hub or the Home app does), pure Rust, async on
Tokio, and `#![forbid(unsafe_code)]` throughout.

```sh
cargo add hap-controller
```

## Why this exists

The Rust HomeKit story had a hole. [`hap-rs`](https://crates.io/crates/hap) is
**accessory**-side (it helps you *build* an accessory). The mature **controller**
implementation — the side that pairs with and drives accessories — is
[`aiohomekit`](https://github.com/Jc2k/aiohomekit), which is Python and lives
behind Home Assistant. If you were writing a smart-home controller, bridge, or
automation in Rust, you had to shell out to Python or reimplement HAP pairing
yourself. HAP pairing is a security-sensitive cryptographic protocol (SRP-6a Pair
Setup, then Pair Verify) — not something you want to hand-roll per project.

`hap-rust` is that missing controller, packaged as a small stack of independently
useful crates.

## Quickstart

```rust
use std::time::Duration;
use hap_controller::{CharValue, CharacteristicType, HapController, JsonFileStore, ServiceType};

#[tokio::main]
async fn main() -> hap_controller::Result<()> {
    // Persists the controller identity and every pairing.
    let store = JsonFileStore::new("./homekit-pairings.json");
    let mut controller = HapController::new(store).await?;

    // Discover, then pair a plug with its 8-digit setup code.
    let found = controller.discover(Duration::from_secs(5)).await?;
    let plug = found.first().expect("an accessory in pairing mode");
    let mut handle = controller.pair(plug, "123-45-678").await?;

    // Find and toggle its On characteristic.
    handle.accessories().await?;
    let (aid, iid) = handle.find(ServiceType::Outlet, CharacteristicType::On)?;
    handle.write(aid, iid, CharValue::Bool(true)).await?;
    Ok(())
}
```

Two types carry the whole API: `HapController` (`discover`/`pair`/`connect`/
`paired`/`remove_pairing`) and `AccessoryHandle` (`accessories`/`find`/`read`/
`write`/`subscribe`/`events`). Subscriptions surface as an async
`Stream<CharacteristicEvent>`. Everything funnels through one `HapError`.

## What's in the box

Each layer is a usable crate on its own; dependencies flow strictly downward:

| Crate | What it gives you |
| --- | --- |
| `hap-tlv8` | HAP's TLV8 wire codec — fragmentation, separators, proptest + fuzz tested. |
| `hap-crypto` | Pair Setup (SRP-6a, SHA-512, HKDF, ChaCha20-Poly1305, Ed25519) and Pair Verify (X25519). |
| `hap-transport` | mDNS `_hap._tcp` discovery, HAP HTTP/1.1, the encrypted record layer, EVENT/1.0. |
| `hap-pairing` | Pair Setup / Pair Verify state machines, `/pairings` management, persistence. |
| `hap-model` | The accessory/service/characteristic database and typed HAP definitions. |
| `hap-controller` | The high-level API that composes all of the above. **Start here.** |

So even if you only need a HAP TLV8 codec, or just the SRP/Pair-Verify crypto,
you can take that one crate.

## How it's verified

Cryptographic primitives are never reimplemented — they come from vetted crates
(RustCrypto / dalek); `hap-rust` implements the HAP *protocols* on top. Every
SRP-6a intermediate value and every Pair Setup / Pair Verify message is
cross-verified byte-for-byte against captured `aiohomekit` traces and the HAP
spec's SRP vectors. The rule on the project: **if our output diverges from
`aiohomekit`, we're wrong by default.**

And it's been driven against real hardware. The full controller lifecycle —
discover → pair (real SRP-6a commissioning) → read/write → subscribe/events →
remove_pairing — was validated end-to-end against a real HomeKit bulb, with the
device's own behavior (it dropped the pairing; its mDNS flag flipped) confirming
each step. That hardware pass also caught a fidelity bug an all-mock test suite
missed (event values that omit their format), which 1.0 fixes.

## Coming from aiohomekit?

There's a call-by-call migration guide: `docs/aiohomekit-migration.md`. The two
shape changes to know about: aiohomekit's callback dispatcher becomes an async
`Stream` from `events()`, and its manual storage dict becomes the `PairingStore`
trait (persisted automatically by `pair`/`remove_pairing`).

## Deferred to 1.x

IP transport only for now. Not yet, but planned: BLE transport (GATT, HAP-BLE),
IP-camera streaming (RTP/SRTP), MFi/hardware auth, the resident-controller role,
Thread transport / Matter bridging, `no_std`, the accessory side, and HAP
service/characteristic types beyond the common set.

## Honest notes

- **Security review.** Correctness is established by byte-for-byte cross-checks
  against `aiohomekit` and the HAP SRP vectors, plus interop pairing with real
  accessories and negative-path tests (wrong code, tampered signatures, replayed
  records). It has **not** had an independent expert cryptographic review. That's
  weaker than such a review at catching subtle side-channel / constant-time
  issues — an accepted, recorded trade-off that may be revisited. Use accordingly.
- **AI assistance.** Developed with significant AI assistance. Every design
  decision was made by a human, every line reviewed, and conformance was verified
  against `aiohomekit`. The code stands on its own merits — read it and judge.
